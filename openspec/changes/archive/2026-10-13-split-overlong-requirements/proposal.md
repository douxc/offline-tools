# Proposal

## Why

`openspec validate --specs --strict` 对主 specs 报出两处「要求正文超过 500 字符」的警告：`visual-system` 的「颜色 token 结构与 shadcn 一致」（602 字符）与 `analytics` 的「关键工具行为事件口径」（510 字符）。

两处成因相同：**一条要求里同时承载了「契约」与「清单」两类内容**。前者把 token 集合、颜色表示法、Tailwind 映射与禁用旧命名四件事压在一段里，后者把上报机制与参数纪律、以及逐个工具的事件覆盖清单压在一段里。这带来两个实际成本：

- 违反「一条要求陈述一种行为」的规格原则，单条要求无法独立判断通过与否 —— 例如「事件覆盖是否完整」与「参数是否取自固定枚举」是两件可以分别失败的事。
- 长正文里嵌着枚举清单，读者难以看出哪部分是必须满足的边界，哪部分是可扩展的成员列表。

## What Changes

- 拆分 `visual-system` 的「颜色 token 结构与 shadcn 一致」为四条要求（该名称保留为其中一条）：
  - **颜色 token 结构与 shadcn 一致**（保留原名）：语义命名与结构、亮暗两态定义位置、禁用旧自定义命名。
  - **必需的语义 token 集合**（新增）：必须覆盖的变量清单。
  - **颜色表示与语义工具类映射**（新增）：颜色值使用 oklch、经 `@theme inline` 映射为 Tailwind 语义工具类。
  - **辅助文字对比度**（新增）：辅助说明/提示/元信息文字对比度 ≥4.5:1，亮暗两态均满足。
- 拆分 `analytics` 的「关键工具行为事件口径」为两条要求（该名称保留为其中一条）：
  - **关键工具行为事件口径**（保留原名）：`_trackEvent` 的 category/action/label 用法、类别与动作取自固定枚举、标签只用站点固定取值、数值只承载无用户语义的计数、禁止上报任何用户数据。
  - **事件覆盖范围**（新增）：逐个工具列出必须上报的完成/失败节点，以及取消记为取消而非失败。
- **被拆要求保留原名并携带其全部既有场景，新增关注点以 `ADDED` 单独成条。** 这是工具约束下的唯一可行形态：`openspec validate --strict` 拒绝 MODIFIED 目标名不存在（`not found`），也拒绝 MODIFIED 块丢失既有场景（`omits scenario(s)`），因此「拆分要求」与「场景随关注点走」不可兼得。
  - 代价：两条保留原名的要求内容已收窄，却必须继续携带原属该块的全部场景，导致**要求名与部分场景之间存在轻微错配**。已在 design 决策 2 记录。
- 拆分只改变要求的**组织方式**，不改动既有语义：拆分后各条要求合起来与被拆要求逐句等价，被拆要求的既有场景全部保留（在 MODIFIED 块内，不迁移、不改写）。
- 因主 specs 只能通过变更修改，本变更以 delta 形式承载拆分结果，经同步后落到主 specs。**不涉及任何代码、测试或产物改动。**

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `visual-system`: 把单条超长要求调整为四条聚焦要求（1 条 MODIFIED 保留原名 + 3 条 ADDED）。
- `analytics`: 把单条超长要求调整为两条聚焦要求（1 条 MODIFIED 保留原名 + 1 条 ADDED）。

## Impact

- 仅影响 `openspec/specs/visual-system/spec.md` 与 `openspec/specs/analytics/spec.md` 的组织结构。
- 不涉及 `src/`、测试、构建配置或产物；无行为变化、无兼容性影响、无破坏性变更。
- 既有实现与自动化断言无需改动：拆分后各条要求对实现提出的约束与被拆要求逐句相同。
- 拆分后 `openspec validate --specs --strict` 的两处「超过 500 字符」警告应消失。
