# Design

## Context

两条主 spec 要求超出验证器的 500 字符阈值，成因是把「契约」与「清单」压在同一段里。这两条要求的场景本身是健康的（各 3 个场景），问题只在正文组织。约束来自项目既有约定：

- 主 specs 只能通过变更（delta）修改，不能直接编辑，因此拆分必须以 `MODIFIED Requirements` 承载。
- 既有 `## Purpose` 段不得改动。
- 被拆要求原有的全部场景必须保留 —— 项目里已发生过「同步时整块替换导致场景静默丢失」（`add-id-photo-tool` 归档时三条三语化场景险些被删），因此场景归属必须逐条交代。
- 验证器按**单条要求的正文长度**判定（`requirements[N]`），阈值 500 字符。

## Goals / Non-Goals

**Goals:**

- 让两条超长要求各自拆成「可独立判断通过与否」的聚焦要求，每条正文 <500 字符。
- 拆分后各条要求合起来与被拆要求**逐句等价** —— 不新增、不删除、不放宽、不收紧任何约束。
- 原有场景全部保留，并归属到语义最贴切的那条要求。

**Non-Goals:**

- 不改动 `src/`、测试、构建配置或产物；本次无任何行为变化。
- 不顺带改写其它要求（包括现存 476 字符的 `圆角与控件尺寸统一`、370 字符的 `路由级 PV 上报` —— 它们未触发阈值）。
- 不重新组织主 spec 的要求顺序或编号。

## Decisions

### 决策 1：按「可独立失败的关注点」切分，而不是按句子长度均分

阈值只是暴露问题的信号，真正的切分依据是「这几部分能不能分别失败」。

`颜色 token 结构与 shadcn 一致`（602 字符）含四类可独立失败的关注点，拆为四条：

| 要求 | 字符 | 关注的失败模式 |
|---|---|---|
| 颜色 token 结构与 shadcn 一致（**原名保留**） | 163 | 命名/结构不符（用了 `--ink` 这类旧命名、亮暗定义位置不对、两主题定义不齐） |
| 必需的语义 token 集合（新增） | 437 | 变量缺失 |
| 颜色表示与语义工具类映射（新增） | 88 | 表示法或映射缺失 |
| 辅助文字对比度（新增） | 52 | 可读性不达标 |

**为什么把对比度独立出来**：它与 token 结构没有因果关系 —— token 结构完全正确时对比度仍可能不达标。原要求把它和结构绑在一起，使「对比度不合格」表现为「token 结构要求失败」，定位错误。

**为什么把命名结构与变量集合再拆一层**：第一版拆分后变量集合仍为 542 字符（变量枚举本身太长）。命名结构（用不用 shadcn 语义命名）与集合完整性（有没有漏变量）也确实可独立失败。这是唯一一处为满足阈值而多拆的一层。

`关键工具行为事件口径`（510 字符）含两类，拆为两条：

| 要求 | 字符 | 关注的失败模式 |
|---|---|---|
| 关键工具行为事件口径（**原名保留**） | 301 | 参数来自用户输入、标签/数值用法越界、上报了用户数据 |
| 事件覆盖范围（新增） | 209 | 某个工具的完成/失败节点漏报 |

**为什么这样分**：参数纪律是「怎么报」，覆盖范围是「报哪些」。前者违反是隐私/合规问题，后者违反是数据完整性问题，处置方式完全不同。

**备选（否决）**：把枚举清单搬进场景。验证器提示里建议了这条，但此处枚举**不是示例而是契约内容** —— 「必须覆盖哪些节点」是要求本身，搬进场景会变成「只验证被举到的那几种」，反而放宽约束。

### 决策 2：被拆要求保留原名，新关注点以 ADDED 单独成条

这是本次唯一受工具约束强制的决策，也是第一版方案被推翻的地方。

**约束**：`openspec validate --strict` 会检查每条 MODIFIED 是否携带该要求在现行主 spec 中的**全部**场景，并明确报错：

> MODIFIED "颜色 token 结构与 shadcn 一致" omits scenario(s) the current spec still has: "语义工具类可用", "辅助文字可读". … a MODIFIED requirement replaces the whole block, so archive refuses to drop them.

**因此不可行的方案**：给拆分出的每条要求起新名字并各自携带相关场景。这样 MODIFIED 的目标名在主 spec 中不存在（校验报 `not found`），而若改回原名，又必须把三条场景全带上 —— 即「拆分要求」与「场景随关注点走」在 delta 语义下不可兼得。

**采用的方案**：被拆要求**保留原名**作为一个关注点的载体，并携带其全部原场景；其余关注点用 `ADDED` 单独成条、带各自的新场景。

**代价（必须正视）**：`颜色 token 结构与 shadcn 一致` 保留原名的同时实质内容已收窄为「语义命名与结构」，但它**必须继续携带**原属该块的 4 个场景（含 `语义工具类可用`、`辅助文字可读`）。因此这两个场景与要求名之间存在轻微错配 —— 它们验证的性质现在由对应的 ADDED 要求更精确地陈述，却仍挂在这个收窄后的要求名下。工具约束下无更干净的形态：改名会被判 `not found`，去掉场景会被判丢场景。

**相应地，ADDED 各条不复用原场景名**（原场景名已作为 MODIFIED 的既有场景存在），改用不重名的新场景，避免同一场景名在同一份 delta 中出现两次：
`必需的语义 token 集合` → `必需 token 齐备`；`颜色表示与语义工具类映射` → `颜色统一以 oklch 表达`；`辅助文字对比度` → `辅助文字在两种主题下均可读`；`事件覆盖范围` → `每个工具的完成与失败都有事件`。

### 决策 2b：场景守恒

原两条要求各 3 个场景，拆分后：`visual-system` delta 共 7 个场景（MODIFIED 4 + ADDED 3），`analytics` delta 共 4 个场景（MODIFIED 3 + ADDED 1）。原场景**全部保留在 MODIFIED 块内**（逐条核对已通过），ADDED 的场景为新写、不替代任何原场景。

### 决策 3：一处例外 —— 为「集合为下限」与「两主题一致」补了正文与场景，但两处都有既有实现与测试支撑

- 「该集合为下限：SHALL NOT 因新增界面配色而削减上述任一变量」：这是把原文「SHALL 至少包含」的语义显式化，未新增约束。
- 新增场景 `两个主题的 token 集合一致`：**这一项有既有测试直接守护** —— `tests/theme-tokens-embed.test.mjs` 的「两个主题的 shadcn 语义 token 集合完全一致」，且测试注释注明它防护的是本项目真实发生过的缺陷（`ed4917f` 一次 CSS 重构弄丢了整个亮色 token 块）。因此这不是凭空新增，而是把已被自动化断言守护、却未写进契约的性质补入。

**同时明确否决了两处「顺手新增」**：

- 曾写「新增界面配色 SHALL 优先复用既有语义 token，SHALL NOT 另起命名」并配一个场景，但**没有任何断言守护它，我也未核实站点是否确实不存在其它颜色变量**，故删除。与「凭空加要求」同理，不容许。
- 未顺带改动 476 字符的 `圆角与控件尺寸统一`：它未触发阈值，改它超出本次范围。

### 决策 4：delta 由 MODIFIED + ADDED 共同承载

- `visual-system`：MODIFIED 1 条（保留原名的 `颜色 token 结构与 shadcn 一致`）+ ADDED 3 条。
- `analytics`：MODIFIED 1 条（保留原名的 `关键工具行为事件口径`）+ ADDED 1 条。

不再使用「多条 MODIFIED」的写法（第一版据此写，被校验判为 `not found`）。因为两条被拆要求都**保留原名**，本变更不构成 RENAMED，也没有任何要求被 REMOVED。

## Risks / Trade-offs

**风险 1：拆分看似纯组织调整，但仍可能误删约束。** 缓解：逐条核对原文每个约束片段都出现在拆分结果中（已做，两处均无缺失）；场景数量与名称逐条核对。

**风险 2：同步时整块替换造成场景静默丢失。** 本项目已发生过一次（`add-id-photo-tool` 归档时三条三语化场景险些被删）。**本次这条风险已被工具兜住**：`openspec validate --strict` 会直接报错拒绝缺失既有场景的 MODIFIED 块，因此不可能再靠人工仔细程度来防。已逐条核对原场景全部保留在 MODIFIED 块内。

**风险 3：为满足阈值而过度拆分，把一条要求切得过碎反而不易读。** 已尽量克制 —— `analytics` 只拆两层，`visual-system` 拆四层且其中只有一层是为阈值而拆。476 字符的 `圆角与控件尺寸统一` 未动，作为「不追求阈值最大化」的界线。
