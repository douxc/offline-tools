# Design

## Context

现状与约束（动机见 proposal.md「Why」）：

- 站点是**无后端的多入口静态站**，7 条路由各有真实 HTML 文件（`index.html`、`video-frame/index.html` …）。构建入口在 `vite.config.ts` 的 `build.rollupOptions.input` 显式列出。
- 外部入口契约：门户 www.colors-cc.top **直接链接目标语言路径**（如 `/zh/video-frame/`、`/ja/video-frame/`），不传语言参数；传入路径携带的语言必须被保留。因此「每条语言路径都有真实 HTML 文件」不是可选的实现细节，而是这套交接方式能否成立的前提。
- **默认语言为英语、位于根路径**；中文从根路径迁到 `/zh/`。既有 7 条中文 URL 不做重定向，其语义变为英语。
- 用户要求语言**跨页面跳转与跨会话保持**，因此偏好持久化不是可选项。
- 7 个入口页的 `<head>` 是**手写的、且与 `src/lib/seo.ts` 的 `SEO_PAGES` 逐字重复**（标题 7/7 命中）。重复靠 `tests/build-output.test.mjs` 的 7 条标题断言防漂移。
- `vite.config.ts` 已有一个**构建期占位符注入机制**：`__SITE_URL__`、`__ANALYTICS_ID__` 由 `siteMetaPlugin` 的 `transformIndexHtml` 注入 HTML、`closeBundle` 兜底 `public/` 静态资源。插件必须排在 `VitePWA(...)` 之前，否则预缓存修订号与实际产物不一致（`tests/site-url-embed.test.mjs` 守护）。占位符机制是三语化必须复用的既有资产。
- `tests/build-output.test.mjs` 断言全部 7 页 `<html lang="zh-CN">`，并写死 7 条标题与 manifest 名称 —— **新增语言即失败**。
- 现有 spec 已把「产物中绝对 URL 的 host 唯一」定为契约（`site-url`），且 `canonical` 每页自指。
- 运行时无任何 i18n 设施；`src/` 约 40 个文件含面向用户中文文案。
- 站点是 PWA（`vite-plugin-pwa` 预缓存 + `registerType: "prompt"`），**离线可用是第一约束**。
- 依赖克制：`dependencies` 共 16 项，无 i18n 库。

## Goals / Non-Goals

**Goals:**

- 语言只有一个定义处：新增语言（或调整标签写法）时，产物、SEO、sitemap、测试断言一并跟随，不需要在 21 个文件里逐处改。
- 每个语言版本的 HTML 在**无 JavaScript**时即已是正确语言（`lang`、标题、正文、noscript 导航），使爬虫不依赖 JS 执行。
- 复用既有占位符注入与 PWA 机制，不引入新的构建阶段或新的部署要求（**不需要任何服务器 rewrite 规则**）。
- 语言解析与切换是纯函数可测的逻辑，不依赖 DOM 之外的环境。

**Non-Goals:**

不引入服务器端渲染或运行时国际化服务；产物仍是纯静态文件。
- 不做旧中文 URL（`/`、`/video-frame/` …）到 `/zh/…` 的重定向 —— 已确认「直接换」。
- 不做繁体中文、语言自动机器翻译、按语言分包按需加载（见决策 8）。
- 不改门户 www.colors-cc.top 的实现。

## Decisions

### 决策 1：语言数据源放在 `src/lib/` 下的纯 TS 模块，构建期与运行期共用

新增 `src/lib/i18n/` 目录承载权威数据：

```
src/lib/i18n/
  locales.ts    语言集合：code(en/zh-CN/ja) / 路径前缀(`` / `/zh` / `/ja`)
                / displayName / htmlLang / ogLocale / hreflang / 是否默认
  routes.ts     语言 x 工具 的规范路径推导（唯一实现）+ 语言化链接生成
  messages/
    en.ts  zh-CN.ts  ja.ts       界面词条（决策 8）
```

`routes.ts` 的「语言化链接生成」是决策 5 与「站内导航与当前语言一致」的落地点：给定「当前解析出的语言 + 目标工具」，产出带正确前缀的路径。**这是全站链接的唯一构造入口**，任何地方直接拼 `/video-frame/` 都会在日语/中文下产生跨语言跳转。

`locales.ts` **不得 import React**，以便 `vite.config.ts` 在 Node 构建期直接 import。这不是遗留代码搬移，而是新 capability `i18n` 的属地：`src/lib/seo.ts` 与 `src/components/tool-seo-content.tsx` 的文案改为按语言从 `messages/` 取值，SEO 元数据（标题/描述/关键词/JSON-LD）与界面词条同属一份语言数据源。

**为什么不是「把 SEO 数据留在 seo.ts，构建期再解析」**：`vite.config.ts` 需要这些值来生成入口页；从 TSX 组件树里取文案既脆弱又要求构建期加载 React。纯数据模块是唯一能同时被两端安全消费的形态。

**备选**：把 SEO 数据放 JSON（构建期易读）→ 否决，失去 TS 类型与「语言 × 路由」完备性检查（缺一个语言就是一个类型错误，这对 7×3 矩阵很值钱）。

### 决策 2：入口页在构建期由插件生成，源里不再保留 21 个手写 HTML

新增一个 Vite 插件 `offline-tools:i18n-entries`：

```
vite.config.ts  plugins: [ i18nEntriesPlugin(), siteMetaPlugin(), react(), tailwindcss(), VitePWA(...) ]
                                  |                    |
                                  |                    +-- 复用：注入 __SITE_URL__ / __ANALYTICS_ID__
                                  +-- 1. configResolved/resolveId：把 /ja/video-frame/ 这类 URL 解析到虚拟入口
                                      2. load()：产出该语言该页的完整 HTML（含 lang/OG/JSON-LD/hreflang/noscript/主题脚本）
                                      3. configureServer()：dev 中间件同样产出，保证 pnpm dev 与产物一致
```

`rollupOptions.input` 随之由 7 个手写路径改为 **21 个语言化入口**（`home@en`、`home@zh-CN`、`home@ja`、…），HTML 内容由 `load()` 从决策 1 的数据源渲染。

**为什么不手写 21 个 HTML**：那正是当前 7 页重复的 3 倍放大，且每次改文案要改 21 处。

**为什么不提交生成的 HTML 到仓库**：会立刻回到「产物与数据源可能漂移」的老问题（当前 7 页靠测试才勉强同步）。生成而非提交，使漂移在结构上不可能。

**代价（必须正视）**：`vite.config.ts` 从配置变为「配置 + HTML 生成器」，是本次最重的一块；且 `pnpm build` 前不再有人工检查的 HTML 可读。缓解见风险 1 与任务中的「生成结果快照断言」。

### 决策 3：复用占位符注入，而不是换一套注入方式

新插件产出 HTML 时**保留** `__SITE_URL__` / `__ANALYTICS_ID__` 占位符，交由既有 `siteMetaPlugin` 注入。

**为什么**：`tests/site-url-embed.test.mjs` 的 host 唯一性与「无残留占位符」断言、以及「插件须在 VitePWA 之前」的顺序约束都是既有契约。新插件若自己写死绝对 URL，就要同时改写这些契约，收益为零。新插件只需保证**排在 `siteMetaPlugin` 之前**（数组顺序），使 21 个入口同样经过 `transformIndexHtml`。

### 决策 4：语言完全由路径决定，不引入参数、不写内联脚本

语言解析只读 `location.pathname`：前缀是 `/ja` 或 `/zh` 即该语言，否则英语。**没有**查询参数解析，**没有**内联跳转脚本。

```
   门户                                   本站
   ----                                   ----
   <a href="https://offline-tools.../zh/video-frame/">
        |
        v
   GET /zh/video-frame/   -->  dist/zh/video-frame/index.html  -->  中文页
                                                                    首帧即中文
                                                                    canonical 自指
                                                                    零重定向、零脚本
```

**为什么这是更好的方案**：门户把语言表达在**链接本身**里，于是「哪个语言」这件事在 HTTP 请求到达时就已经确定，不需要任何运行期推断。由此得到三个性质：爬虫拿到的就是对应语言的 HTML（不依赖 JS 执行）；无 JavaScript 时行为完全一致；不产生「先英语后中文」的闪烁或额外导航。这也直接满足「从外部跳转进入时要保留传入的语言设置」—— 传入语言就是路径本身，没有可被偏好覆盖的中间层。

**备选（曾在探索阶段采用，现已否决）**：门户传 `?lang=ja`，入口页内联脚本在首帧前 `location.replace` 到 `/ja/`。否决理由是它把语言决定推迟到客户端脚本，代价是每次门户跳转多一次导航、多一个必须早于首帧执行的脚本、以及「参数与路径不一致时以谁为准」的额外规则 —— 而收益只是门户少写一点 URL。

**代价**：门户的链接必须带语言前缀才能把访客送到非英语版本。英语因占据根路径，任何不带前缀的链接都落到英语 —— 这既是默认语言的语义，也意味着门户若只会上无前缀 URL，就只能送访客到英语版。

### 决策 5：语言解析优先级 —— 路径 > 已保存偏好 > `navigator.language` > 英语

```
  来源                  性质            是否覆盖已保存偏好
  ----------------------------------------------------------
  URL 路径前缀           URL 明确指定     是
  已保存偏好            历史意图          —
  navigator.language    环境推断          —
  默认 en               兜底              —
```

`resolveLocale({ pathname, stored, navigator })` 是纯函数：路径前缀命中即返回该语言；否则取 stored；否则取 navigator 的最近匹配；否则英语。**没有查询参数这一层**（决策 4）。

**为什么路径要压过 stored**：门户直链 `/zh/video-frame/` 的语义是「请给我中文」。若被接收者的历史偏好覆盖，门户的链接就会失效 —— 这直接违背 `i18n` spec 的「支持外部直链并保留传入语言」。

**站内链接必须跟随「解析出的语言」而非「当前路径前缀」**：这是决策 4 去掉参数后出现的连带约束。若站内链接一律照搬当前路径前缀，则「偏好为中文的用户在 `/` 看到中文、点任一链接就掉回英语」—— 语言保持会形同虚设，用户每次都要重新选语言，直接违背「切换语言之后访问其他页面要保持之前的语言」。因此站内链接的前缀取自 `resolveLocale` 的结果（路径 > stored > navigator），而非 `pathname` 的现有前缀。这样链接目标与页面实际渲染的语言始终一致，也保证了同语言内跳转仍可走 `pushState` 而不触发整页加载。

**切换器的写入语义**：切换语言时**写入** stored，包括切到英语（写 `en`）。**不采用「切回默认语言就清除偏好」**的写法 —— 用户要求「切换语言之后……重新访问都要保持之前的语言」，若切到英语时清除偏好，该用户下次打开 `/` 会跟随浏览器语言，可能得到中文或日语，偏好保持即告失效。因此三种语言一视同仁地持久化。

**偏好只在显式选择时改写**：以已保存偏好渲染 `/` 不构成新的显式选择，因此不改写偏好；这避免了「英语根路径把所有人的偏好刷成英语」。

**实现注意（hydration）**：入口页是构建期静态 HTML，其中的链接目标已经写死。若客户端按「已保存偏好」渲染出不同的 `href`，与该静态 HTML 不一致的部分会在 hydration 时报错（React 会按服务端结构纠正）。因此语言化链接生成必须尊重首屏 HTML 的语言：只在**确定的客户端上下文**（例如 `/` 上已按偏好渲染的页面，或切换语言后）产出带前缀的目标，其余情况与所选语言的静态 HTML 保持一致。这条不影响 spec 的对外行为，但决定实现方式，实施时须专门验证三种语言的页面都无 hydration 警告。

### 决策 6：客户端导航分两类，语言切换走整页导航

- **同语言内工具切换**：沿用 `navigateToTool` 的 `pushState` + `popstate`，保持现有「压缩↔水印↔A4 常挂载、不丢已导入图片」的行为。
- **跨语言切换**：用 `window.location.assign` 整页导航。

**为什么跨语言不能 pushState**：语言改变会连带改变 `<html lang>`、`canonical`、`hreflang`、JSON-LD 与全部正文。这些在静态 HTML 里，运行时改一遍等价于重写整个文档头，漏一处就产生自相矛盾的页面。整页导航让浏览器加载**该语言真实存在的那份 HTML**，从根上避免不一致。代价是一次完整加载，但语言切换本就是低频、有意的操作。

### 决策 7：`hreflang` 与 `sitemap` 由同一数据源闭合生成

`locales.ts` + `routes.ts` 同时驱动：每页 `<head>` 里的 4 条 alternate（`zh-CN` / `en` / `ja` / `x-default`），以及 `sitemap.xml` 的 21 条 URL + `xhtml:link` 互指。

`public/sitemap.xml` 目前是手写静态文件且 7 条。**决定**：改为构建期生成（由新插件在 `closeBundle` 写入 `dist/sitemap.xml`，或保留一个含占位符的模板由新插件展开）。理由与决策 2 相同 —— 21 条互指关系手写必然出错，而 `tests/site-url-embed.test.mjs` 会校验闭合性。

**`x-default` 指向英语版**（根路径）：英语是站点默认语言，与决策 5 的兜底一致。

### 决策 8：i18n 运行时自建，不引入 i18n 库；词条按函数条目组织

新增约 150 行的 `LocaleProvider` + `useT()`（React context，无外部依赖）。词条为**函数条目**：

```ts
// messages/ja.ts
export const ja = {
  "frame.export.success": (n: number) => `${n} 枚のフレームを書き出しました（ZIP）`,
  "nav.video": "動画",
  ...
}
```

**为什么不用 `react-i18next` / `react-intl`**：站点是离线 PWA，三份词条必须全量进包（懒加载语言会在离线时失败）。包体积不是问题（现有 `main.js` 551 KB，三语词条预估 +20–30 KB），真正的问题是这两条：现有动态文案是**带参数插值的中文模板**（如 `已导出 ${times.length} 张帧（ZIP）`），函数条目天然覆盖，而 ICU 复数/i18n 库的插值语法要为日英重写一遍；且项目依赖极为克制，没有为 150 行能力换一个运行时依赖的理由。

**代价**：自己实现的插值与「缺失词条」检测不如库完善 → 由任务中的「词条完备性类型检查 + 残留中文扫描测试」补上。

### 决策 9：文案抽取的机械部分由扫描测试兜底

约 40 个文件的中文串抽取是本次最大的一块**机械**工作量，人工必然遗漏。补一个**残留中文扫描**断言：对渲染路径可达的源文件，在已抽取区域之外不得出现中文字符（允许注释与用户数据）。同时用 TS 类型保证三种语言的键集合完全一致（`Record<MessageKey, …>` + 键来自 key 联合类型）。

## Risks / Trade-offs

**风险 1：构建期生成 HTML 让 `vite.config.ts` 变复杂，且 dev 与 build 两条路径可能产出不一致** → 生成逻辑集中在单一模块，dev 中间件与 `load()` **共用同一个渲染函数**（不允许两套模板）；任务中显式安排「`pnpm dev` 抓取入口 HTML」与「构建产物」的一致性断言。

**风险 2：21 个入口中若某个语言变体的占位符未被替换，会留下 `__SITE_URL__` 进产物** → 沿用既有 `site-url-embed.test.mjs` 的「无残留占位符」断言，它天然覆盖新增入口；新插件须排在 `siteMetaPlugin` 之前。

**风险 3：入口页从 7 变 21，PWA 预缓存体积与修订号随之变化** → `globPatterns` 已含 `*.html`，21 份 HTML 约 180 KB，预缓存增量可接受；但因改了插件顺序，必须重跑 `tests/site-url-embed.test.mjs` 的修订号一致性断言，任务中单列。

**风险 4：门户若只会上无前缀 URL，就只能把访客送到英语版** → 这是直链契约的固有要求，已在决策 4 说明代价。门户按同一模板拼前缀即可（无前缀＝英语，`/zh`＝中文，`/ja`＝日语）；且 `hreflang` 与 `sitemap` 会把三个语言版本互相暴露给搜索引擎，即使门户只链一种语言，另两种仍可被独立收录。

**风险 5：翻译质量，尤其 en/ja 的 SEO 标题与关键词是人工判断而非机械替换** → 提案与 spec 已明确「按检索习惯改写而非直译」；任务中把「7 个工具 × 2 语言」的标题/描述/关键词作为需要人工确认的产出单列，不由构建流程自动生成。

**风险 6（已排除）：曾担心语言进入路径后百度统计 PV 由 7 条裂为 21 条** → 查证 `src/lib/route-analytics.ts` 后确认**不成立**：上报用的是 `SEO_PAGES[route].path`（语言无关的工具路径，如 `/video-compress/`），不是 `window.location.pathname`。语言路径不进 PV，统计无需改动、报表口径不变。

**风险 7：`<html lang>` 的中文标签写法选择会影响既有搜索表现** → **决定沿用 `zh-CN`**：它是既有页面已在用的取值，改成 `zh-Hans` 只会平白重置信号，而收益仅是方言精确度。spec 只要求「一种语言只有一种写法」，`zh-CN` 满足该要求；若日后要改标签，只动 `locales.ts` 一处。

**风险 8：中文版从根路径迁到 `/zh/` 且不做重定向，会损失中文自然流量** → 这是已确认接受的代价（用户选择「直接换」）。可缓解的部分：`hreflang` 与 `sitemap` 会让搜索引擎尽快发现 `/zh/…` 的新地址；标签沿用 `zh-CN` 保留语言信号；英文页在旧地址上承接原有链接权重。**不可缓解**：既有指向 `/video-frame/` 的中文外链与书签现在会打开英语页，若中文流量占比高，应在发布后主动向搜索引擎提交新 sitemap 并观察排名变化。

## Migration Plan

1. **先建数据源与生成器，不改任何文案、不换默认语言**：以现有中文文案填入 `messages/zh-CN` 与 SEO 数据，仅生成 7 个**位于根路径**的中文入口，并与现有手写 HTML 逐字节比对，确保「生成 = 现状」。此时也一并解决既有 index.html 与 `SEO_PAGES` 的已知不一致（如果比对暴露出来）。
2. **加语言与切换默认**：补 `en`/`ja` 词条与 SEO 数据；入口改为 21 个，英语落根路径、中文落 `/zh/`、日语落 `/ja/`；加 `routes.ts` 的语言化链接生成、语言解析与页头切换器；写入 `hreflang` 与生成 sitemap。此步是 URL 语义变化真正生效的一步。
